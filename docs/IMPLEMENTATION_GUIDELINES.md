# MVP implementation guidelines

Build the smallest clear implementation that satisfies the [requirements](MVP_REQUIREMENTS.md) and [contract](../contracts/v0.1/CONTRACT.md). These rules apply to every implementation issue. Keep the existing stack and useful branch code; change only what the accepted feature or contract requires.

## Keep the architecture small

- One React/Vite UI, one FastAPI application, one PostgreSQL-backed worker and the existing Supabase database/storage are the MVP baseline.
- Use ordinary functions and explicit data flow. Add a class or shared abstraction only when it removes real duplication or protects a concrete boundary. Avoid generic agent/plugin frameworks, base repositories, dependency-injection containers and one-line forwarding layers.
- Reuse the existing LangGraph code where it helps. A deterministic sequence can be a function; no new graph, autonomous planner or multi-agent conversation is required for each feature.
- Use the existing workflow table for durable work. Implement the required claim/lease, retry and atomic completion rules there; no Redis, external queue, event bus or distributed workflow platform is required.
- Prefer the contract's simple staging/reconciliation option for export files. An outbox service is not required. Crash recovery and orphan cleanup still need to work.
- Capability reports can be generated by a small deployment-check script and stored as validated records/files. Provider routing can be server configuration. Neither needs an admin application or standalone service.
- Learning plans do not need template authoring or publication. Future independent assessments require reviewed criteria; keep their review process separate from learner acceptance.
- Do not add infrastructure or a dependency for a hypothetical future use case. If one is necessary for an acceptance criterion, explain the need and the simpler option considered in the implementation PR.

## Put code where its responsibility belongs

These are responsibility boundaries using the existing branches, not a request to create empty directories or reorganize the repository up front. Add a file only when there is working code for it.

| Area | Location and responsibility |
| --- | --- |
| UI pages/components | Keep `src/pages` for screen composition and `src/components` for reusable controls/activity renderers. Reuse the current design and routing. |
| UI API/state | Keep `src/lib/api` for the shared HTTP client and typed endpoint functions; `src/hooks` for fetching, polling and feature state. Server records are authoritative; avoid duplicate journey state stores. |
| API | Keep `careerbridge/main.py` for app setup and route registration. Small domain route modules handle validation/authentication and call domain functions; they contain no prompts or SQL. |
| Work execution | Keep `careerbridge/worker.py` for claiming work, dispatch, retries and completion. Business decisions belong in domain modules. |
| Domain logic | Reuse `analyst.py`, `search_agent.py`, `learning_coach.py` and `assessor.py`; add focused grading/export modules when needed. Use plain functions with explicit inputs/results. |
| Model access | A small `careerbridge/model_gateway.py` owns client construction, server routing, deadlines, retries and output validation. Share the compatible transport for OpenAI/Nebius; keep provider-specific differences here. |
| Prompts | Keep trusted task instructions in `careerbridge/prompts/`, next to other prompts for that domain. Do not embed long prompt strings in routes, worker dispatch or UI code. |
| Persistence | Use the existing `database/` package and its domain modules. All schema changes use versioned migrations. Remove the agent branch's competing schema initialization when integrating it. |
| Competency content | Reviewed template data and resources are versioned content. Grading functions are code. Real private tests/answers stay in private storage. |

The API/schema contract is the source of truth. Generate or mechanically check UI types against it; do not maintain a second informal API definition. Domain code should not depend on a particular provider SDK.

## Use a practical physical schema

`data-model.yaml` describes logical records and their required invariants; its 36 entries are **not a requirement for 36 physical tables or repository classes**. Extend the existing schema deliberately. Stable snapshots and reviewed template documents can use validated JSONB where that makes the implementation clearer.

Before implementing a DB slice, include a short logical-to-physical mapping in the migration PR. Record which existing/new table or JSON field holds each affected record, how stable IDs/references resolve, and where ownership, uniqueness, immutability and atomic writes are enforced. Update that mapping with migrations. Use ordinary columns/constraints where joins, ownership or concurrent updates need them. Consolidation must preserve all API behavior and contract invariants; it must not replace transactional checks with unchecked JSON.

## Write specific prompts

Each model task has a named, versioned prompt with one job and an explicit output contract. Use this short structure, adapting the sections to the task:

```text
Task: <one bounded action>
Inputs: <named fields, sources and what they mean>
Rules: <evidence allowed, limits, and decisions the model cannot make>
Missing evidence: <the schema-supported empty/unknown result>
Output: <schema ID/version, or a defined text format and length bound>
```

Pass external text as clearly identified data, separate from trusted instructions. Do not interpolate user text into system instructions. Include only the context that task needs. Use a schema reference or generated format instructions rather than manually repeating a second schema in the prompt.

- Extraction: use supplied source text, preserve supporting excerpts, and never infer missing credentials or experience.
- Gap analysis: use confirmed skills and sourced requirements; explain missing evidence without treating it as demonstrated inability.
- Learning: use the selected reviewed template, milestone and allowed resources; never supply private grading keys or invent executable activities.
- Assessment feedback: explain an already computed deterministic result; do not ask a model to decide pass/fail or modify a rubric.
- Résumé drafting: propose only claims supported by confirmed experience or verified evidence; do not convert an exercise into employment or production experience.

Define what to do for empty, conflicting or insufficient inputs. Validate structured output and evidence references in code before persistence; prompting alone is not enforcement. Keep provider selection out of prompts. Avoid broad personas, repeated instructions and speculative instructions unrelated to the task.

## Keep changes readable and verifiable

Prefer descriptive names, explicit branches, early validation and small cohesive functions. Concise means easy to follow, not compressed one-liners or arbitrary line-count limits. Comment on reasons and invariants, not obvious syntax. Remove superseded code in the touched path; keep unrelated cleanup separate.

Every implementation PR must:

- Link its issue and acceptance criteria, and identify the modules changed and why.
- Include only the feature and refactoring needed to implement it; justify new dependencies/services/tables or abstractions.
- For prompt changes, show the prompt version/schema and representative normal, missing-evidence and adversarial-input results. Run real provider checks when changing provider behavior or deploying a new prompt/model combination.
- Prove meaningful behavior at boundaries: ownership, output validation, idempotency/recovery, grading and approval when touched. Reuse shared fixtures; do not add tests that merely restate implementation details.
- Pass applicable type/lint/build checks and contract checks; keep demo fixtures explicit and preserve existing release gates.

P1 wellbeing and broader activity families remain deferred. Simplicity does not remove authentication, reviewed templates, independent grading, durable results or exact résumé approval.
